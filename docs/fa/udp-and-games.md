# فوروارد UDP و بازی

[English](../udp-and-games.md) · **فارسی**

## قانون‌های UDP

```toml
[[forward]]
listen = "0.0.0.0:51820"
target = "127.0.0.1:51820"        # e.g. WireGuard on the exit
protocol = "udp"                  # or "tcp+udp" for both on one port
```

- **هر آدرس client یک جریان (flow) است.** خروجی برای هر جریان یک سوکت جدا به مقصد می‌دهد، پس پاسخ‌ها به client درست برمی‌گردند.
- **بسته‌ها مرزهایشان را نگه می‌دارند** و هرگز ادغام یا تکه نمی‌شوند.
- **صفِ پر بسته را می‌اندازد، هرگز متوقف نمی‌کند.** وقتی تانل نتواند برسد، بسته‌ها همان‌طور که شبکه می‌انداخت افتاده می‌شوند.
- **جریان‌ها بعد از `tuning.udp_timeout_secs`** (پیش‌فرض ۶۰) بدون بسته تمام می‌شوند. `tuning.udp_max_flows` (پیش‌فرض ۱۰۲۴ برای هر قانون) clientها را محدود می‌کند.
- **برای UDP از mux استفاده کنید.** بدون آن هر جریان یک اتصال کامل تانل لازم دارد و `kariz check` هشدار می‌دهد.

اینکه بسته چطور می‌رود به ترنسپورت بستگی دارد:

| ترنسپورت | بسته‌های UDP چطور می‌روند | بستهٔ گم‌شده |
|---|---|---|
| `tcp`، `tcpmux`، `ws`، `wss` | داخل stream در TCP | دوباره فرستاده می‌شود؛ همهٔ پشتش منتظر می‌ماند |
| `quic` | به‌صورت datagramهای QUIC (بزرگ‌ها روی stream) | گم می‌شود؛ هیچ‌چیز منتظر نمی‌ماند |
| `kcp` | کنار stream در KCP، مهرشده با کلیدهای session | گم می‌شود، یا FEC بازسازی‌اش می‌کند؛ هیچ‌چیز منتظر نمی‌ماند |

## بازی

پیکربندی پیشنهادی، در [`configs/entry-gaming.toml`](../../configs/entry-gaming.toml) و [`configs/exit-gaming.toml`](../../configs/exit-gaming.toml):

```toml
profile = "gaming"                # on both sides

[tunnel]
transport = "kcp"

[[forward]]
listen = "0.0.0.0:27015"
target = "10.0.0.2:27015"
protocol = "tcp+udp"
duplicate = 2                     # each UDP packet twice, both ways
```

روی یک مسیر شبیه‌سازی‌شدهٔ ۶۰ms و ۵۰ Mbit/s اندازه گرفته شده. ترافیک بازی بسته‌های ۱۲۸ بایتی است، ۶۴ تا در ثانیه، که هرکدام برگردانده می‌شود. جدول p50 / p99 رفت‌وبرگشت را به ms و سهم بسته‌هایی را که برگشتند نشان می‌دهد.

| اتلاف | ترنسپورت | تانل بی‌کار | کنار ۴ دانلود |
|---|---|---|---|
| 1 % | `tcpmux` | 62 / 169, 100 % | 395 / 734, 100 % |
| 1 % | `kcp`, UDP در stream (v0.4) | 63 / 141, 100 % | 86 / 219, 100 % |
| 1 % | `kcp`, پروفایل gaming | 63 / 69, 100 % | 66 / 82, 100 % |
| 5 % | `kcp`, UDP در stream (v0.4) | 63 / 236, 100 % | 144 / 347, 100 % |
| 5 % | `kcp`, پروفایل gaming | 63 / 84, 99.0 % | 68 / 94, 99.4 % |
| 5 % | `kcp`, پروفایل gaming، ۲ کپی | 63 / 70, 99.5 % | 67 / 91, 100 % |
| 5 % | `quic`, ۲ کپی | 63 / 78, 99.2 % | 91 / 154, 94.4 % |

چه چیزی فرق می‌سازد:

- **بستهٔ بازی هرگز منتظر بستهٔ گم‌شده نمی‌ماند.** روی `kcp` کنار stream قابل‌اعتماد می‌روند؛ روی ترنسپورت‌های مبتنی بر TCP هر بسته منتظر ارسال دوبارهٔ segment گم‌شده می‌ماند.
- **FEC بیشتر اتلاف‌ها را** در یک بازهٔ KCP (۲۰ms با `fast2`) بازسازی می‌کند، به‌جای اینکه گم شوند.
- **پروفایل gaming نمی‌گذارد دانلودها مسیر را پر کنند.** پنجرهٔ stream ‏۶۴ KiB صف مسیر را کوتاه نگه می‌دارد، پس بسته‌های بازی در آن منتظر نمی‌مانند.
- **`quic` زیر اتلاف برای بازی ضعیف‌تر است.** quinn datagramها را زیر همان کنترل ازدحام streamها می‌فرستد، که زیر اتلاف تصادفی کند می‌شود. بعد از یک انفجار طولانی اتلاف، datagramها را چند صد میلی‌ثانیه نگه می‌دارد.

اعداد کامل، از جمله اتلاف انفجاری، در [کارایی](performance.md) است.

## دوبل‌کردن بسته

`duplicate = 2` (یا ۳) روی یک قانون UDP هر بسته را به همین تعداد بار در مجموع می‌فرستد، در هر دو جهت، با فاصلهٔ `duplicate_gap_ms` (پیش‌فرض ۵). گیرنده کپی‌ها را دور می‌ریزد.

- **کجا کمک می‌کند:** فقط روی `kcp` و `quic`، و فقط جایی که بسته ممکن است گم شود. بسته‌هایی که قابل‌اعتماد می‌روند (در stream) یک‌بار فرستاده می‌شوند.
- **چه می‌کند:** روی مسیری که در هر جهت ۱۰٪ گم می‌کرد، بسته‌های بازیِ برگشتی با ۲ کپی ۰٫۵ تا ۳٫۵٪ رفت‌وبرگشت‌ها را گم کردند، در برابر ۲۱ تا ۲۳٪ بدون آن.
- **چقدر خرج دارد:** پهنای‌باند آن قانون ضرب‌در تعداد کپی. برای یک بازی معمولی حدود ۱۰۰ kbit/s، ولی برای WireGuard یا UDP حجیم جدی است، پس فقط روی قانون‌های بازی یا صدا بگذاریدش.
- **سازگاری:** خروجی باید v0.5 یا جدیدتر باشد؛ خروجی نسخهٔ v0.4 آن جریان‌ها را رد می‌کند و ورودی آن را لاگ می‌کند.

## DSCP

`[tuning] dscp = "ef"` (یا `af41`، `cs4`، ... یا عددی ۰ تا ۶۳) سوکت‌های تانل و سوکت‌های UDP از خروجی به مقصدها را علامت می‌زند، برای شبکه‌هایی که ترافیک علامت‌دار را اولویت می‌دهند.

- **به‌طور پیش‌فرض خاموش است.** روی اینترنت عمومی علامت معمولاً پاک یا نادیده گرفته می‌شود، بعضی شبکه‌ها با ترافیک علامت‌دار بدتر رفتار می‌کنند و علامت غیرمعمول یک جریان را متمایز می‌کند.
- **روی لینک‌هایی که خودتان اداره می‌کنید کمک می‌کند**، یا با یک queueing discipline مثل `fq` یا `cake` روی سرور.
- **سوکت‌های QUIC علامت نمی‌خورند:** quinn بایت TOS هر بسته را خودش می‌گذارد.
- **ویندوز علامت را نادیده می‌گیرد** مگر اینکه سیاست QoS اجازه بدهد.

## MTU

`kcp` بسته‌های UDP تا حدود ۱۳۰۰ بایت را کنار stream خودش جا می‌دهد؛ بزرگ‌تر از آن از stream می‌رود. datagramهای `quic` حدود ۱۲۰۰ بایت جا دارند. برای WireGuard روی هرکدام، MTU اینترفیس WireGuard را ۱۲۸۰ بگذارید تا بسته‌هایش روی مسیر سریع بمانند.
