# ترنسپورت Paqet روی TCP خام

Paqet برای تونل‌های کاریز روی لینوکس و IPv4 است. بسته‌های رمزنگاری‌شده و
احرازهویت‌شدهٔ KCP داخل بسته‌های TCP خام قرار می‌گیرند. کاریز سربرگ TCP را
می‌سازد و لینوکس مسیریابی بسته‌ها را انجام می‌دهد. هر دو سمت به کاریز
`2.8.0-beta.1` یا جدیدتر و دسترسی `CAP_NET_RAW` نیاز دارند. سرویس تونل کاریز
این دسترسی را دارد.

یک پورت اختصاصی TCP و آدرس IPv4 محلیِ سرور شنونده انتخاب کنید. پنل آدرسی را
پیش‌فرض می‌گذارد که مسیر سرور شنونده به اینترنت از آن خارج می‌شود. در حالت
`reverse` ورودی گوش می‌دهد و خروجی وصل می‌شود. در حالت `direct` خروجی گوش
می‌دهد و ورودی وصل می‌شود. قواعد فایروالِ لازم را خود کاریز روی هر دو سمت
اضافه می‌کند (پایین‌تر را ببینید).

## نمونهٔ تونل reverse

با `kariz token` یک توکن بسازید و همان را در هر دو سمت بگذارید. آدرس‌ها و
مقصد فوروارد نمونه را با مقادیر خودتان عوض کنید.

```toml
# ورودی، سمت شنونده
role = "entry"
mode = "reverse"

[tunnel]
transport = "paqet"
listen = "192.0.2.21:31080"
token = "CHANGE-ME-run-kariz-token"

[tunnel.kcp]
mtu = 1200

[[forward]]
listen = "0.0.0.0:18080"
target = "127.0.0.1:18081"
protocol = "tcp+udp"
```

```toml
# خروجی، سمت وصل‌شونده
role = "exit"
mode = "reverse"

[tunnel]
transport = "paqet"
remote = "192.0.2.21:31080"
token = "CHANGE-ME-run-kariz-token"

[tunnel.kcp]
mtu = 1200
```

## فایروال هر دو سمت

بسته‌های Paqet بدون دست‌دهی TCP داده حمل می‌کنند. بدون قاعده، کرنل به هر کدام
پاسخ TCP Reset می‌دهد و connection tracking آن‌ها را نامعتبر علامت می‌زند. فایروالی
که فقط پاسخ اتصال‌های برقرار را می‌پذیرد (مثل ufw یا firewalld) این بسته‌ها را
دور می‌ریزد و تونل هیچ‌وقت وصل نمی‌شود.

برای همین کاریز چهار قاعدهٔ `iptables` را بالای زنجیره‌هایشان اضافه می‌کند. در
سمت شنونده این قواعد به آدرس و پورت شنونده محدودند. در سمت وصل‌شونده به آدرس
وصل‌شونده و آدرس و پورت شنونده محدودند، تا هر اتصال دوباره از همان قواعد استفاده
کند:

| جدول و زنجیره | چه بسته‌ای | کار |
| --- | --- | --- |
| `raw PREROUTING` | بسته‌های ورودی تونل | `CT --notrack` |
| `raw OUTPUT` | بسته‌های خروجی تونل | `CT --notrack` |
| `filter INPUT` | بسته‌های ورودی تونل | `ACCEPT` |
| `filter OUTPUT` | TCP Resetهای خروجی تونل | `DROP` |

قواعد توضیح `kariz-paqet pid=<pid>` دارند و با توقف تونل حذف می‌شوند. اگر پردازه
به‌زور بسته شده باشد، اولین تونل Paqet که بعداً روشن شود قواعد باقی‌مانده را پاک
می‌کند. برای دیدنشان `sudo iptables -S | grep kariz-paqet` و
`sudo iptables -t raw -S | grep kariz-paqet` را اجرا کنید.

فایروالی که جلوی سرورهاست (مثل فایروال ارائه‌دهندهٔ ابری) روی خود میزبان نیست.
پورت TCP تونل را آنجا خودتان باز کنید.

### بدون iptables

اگر `iptables` نصب نباشد یا خطا بدهد، تونل باز هم روشن می‌شود و لاگ سرویس هشدار
می‌دهد. در این حالت قواعد معادل را خودتان بگذارید. متغیرهای زیر را روی هر دو
میزبان با آدرس‌ها و پورت خودتان تنظیم کنید. اگر فایروال با سرویس دیگری مدیریت
می‌شود، از قواعد معادل و روش ذخیره‌سازی همان سرویس استفاده کنید.

```bash
listener=192.0.2.21
dialer=192.0.2.22
port=31080
action=-I
```

روی سمت شنونده:

```bash
sudo iptables -w "$action" INPUT -s "$dialer" -d "$listener" -p tcp --dport "$port" -j ACCEPT
sudo iptables -w "$action" OUTPUT -s "$listener" -d "$dialer" -p tcp --sport "$port" --tcp-flags RST RST -j DROP
```

روی سمت وصل‌شونده:

```bash
sudo iptables -w "$action" INPUT -s "$listener" -d "$dialer" -p tcp --sport "$port" -j ACCEPT
sudo iptables -w "$action" OUTPUT -s "$dialer" -d "$listener" -p tcp --dport "$port" --tcp-flags RST RST -j DROP
```

اگر سیاست خروجی محدود است، ترافیک خروجی تونل را بعد از قاعدهٔ حذف RST مجاز
کنید. برای حذف، همان دستورها را با `action=-D` اجرا کنید.

فایروال‌های حالت‌دار و NAT بین دو میزبان ممکن است بسته‌ها را حذف کنند.
مسیر را با یک درخواست واقعی از تونل بررسی کنید. برای عیب‌یابی لاگ سرویس یا
خروجی `tcpdump -ni any 'tcp port 31080'` را در هر دو سمت ببینید.

## تنظیم کارایی

Paqet از [تنظیمات KCP](configuration.md#tunnelkcp-kcp) برای زمان‌بندی، پنجره‌ها،
MTU، ‏FEC و دیتاگرام استفاده می‌کند. مالتی‌پلکس به‌صورت پیش‌فرض روشن است و
چندین اتصال فورواردشده را روی لینک مشترک حمل می‌کند. کرنل بسته‌های پورت‌های
دیگر را فیلتر می‌کند و در سمت وصل‌شونده بسته‌های آدرس‌های مبدأ دیگر را هم. کاریز
بافر بسته را دوباره به‌کار می‌گیرد و قبل از ساخت نشست KCP، بسته را احراز هویت
می‌کند.

هر جریان مثل یک اتصال واقعی شمارهٔ sequence و acknowledgment خودش را دارد. پس
فایروال حالت‌دارِ بین راه هر اتصال مالتی‌پلکس را داخل پنجرهٔ خودش می‌بیند. بافر
سوکت خام حتی بالاتر از `net.core.rmem_max` و `wmem_max` روی اندازهٔ بافر سوکت
`[tuning]` تنظیم می‌شود تا بسته‌های یک انفجار ترافیک به‌خاطر پیش‌فرض کوچک از دست
نروند.

پیش‌فرض MTU برابر ۱۳۵۰ است. اگر MTU مسیر کمتر است، این مقدار را در هر دو سمت
کم کنید. ۱۲۰۰ نقطهٔ شروع است. دست‌کم ۷۰ بایت از MTU مسیر IPv4 کم کنید و با
FEC دست‌کم ۸۳ بایت. سقف تنظیم در کاریز ۱۴۳۰ و با FEC برابر ۱۴۱۷ است.

از پیش‌فرض‌ها شروع کنید. حالت `normal` نسبت به `fast2` با فاصلهٔ بیشتری بسته‌ها
را تخلیه می‌کند. پنجره‌های کوچک‌تر صف را کم می‌کنند و ممکن است روی مسیر طولانی
یا پراتلاف سرعت را پایین بیاورند. FEC بستهٔ اضافی و پردازش بیشتری می‌خواهد.
تعداد اتصال‌ها، keepalive، بافر سوکت و DSCP از همان `[tunnel.mux]` و `[tuning]`
تنظیم می‌شوند.

Paqet برای هر تونل صریح انتخاب می‌شود. قالب بسته‌ها و کلید مشتق‌شده از توکن
مختص کاریز است.
